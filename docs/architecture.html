manim-demos 架构文档

十二个解释性参考场景的透明 PNG 与短时动画集合，以可程序化复现的方式交付数学、算法与系统概念的可视化论证。

产品概述

manim-demos 是一个基于 Manim（数学动画引擎）构建的教学可视化场景集合。 每个场景围绕一个具体的知识问题展开——从二分查找的区间不变性，到傅里叶级数的相量合成，再到贝叶斯更新的分布演化—— 并以两种形式交付：透明背景 PNG（主产物，用于文档、幻灯片嵌入）和 低分辨率 MP4（辅产物，保留时间维度的论证过程）。

项目采用「目录驱动 + 脚本渲染 + 契约测试」的极简架构：场景定义集中在一个源文件中，渲染流程由一个 Python 脚本统一调度， 输出质量通过像素级校验和文件契约测试双重保障。所有产物均纳入版本控制，确保可追溯、可复现。

架构总览

图 1 · 分层架构
从场景元数据到最终产物的四层结构：数据定义、场景实现、渲染调度、输出交付。

四层自顶向下的单向数据流。最顶层的 catalog.json 是场景元数据的唯一真相源， 记录每个场景的教学用途、核心问题、视觉家族、复杂度和标签——它不参与代码运行，而是作为文档索引和发现机制存在。

场景层（scenes.py）是项目的核心资产。十二个 Manim Scene 子类在同一个文件中定义， 共享统一的配色（墨青、琥珀、玫瑰、靛蓝、紫罗兰）和标题块样式，确保视觉语言一致。 每个类在 __init__.py 的 SCENES 字典中注册，slug 到类名的映射是渲染器查找场景的唯一入口。

调度层（render.py）是连接场景定义与最终产物的桥梁。它遍历 SCENES 字典， 对每个场景执行两次 Manim 渲染（静帧 + 动画），将产物从临时媒体目录拷贝到 out/， 并运行像素级和视频时长校验。这一层是「构建系统」的全部——没有 Makefile，没有 CI 配置， 一个脚本即完整流水线。

交付层（out/）存放最终产物。24 个文件（12 PNG + 12 MP4）全部纳入 Git 管理， 使下游消费者可以直接引用，而无需本地搭建 Manim 环境。右侧的 test_contract.py 是质量守门人：它确保每个已注册的场景都有对应产物，且视频文件非空。

渲染流水线

图 2 · 单场景双次渲染流水线
每个场景经历两次 Manim 调用，分别产出透明静帧和过程动画，随后经过双重校验。

双次渲染是本项目的核心设计决策。第一次调用 manim -ql -s -t （低质量 + 末帧模式 + 透明背景）渲染场景的最后一帧为带 alpha 通道的 PNG。 -s（--skip_animations 的变体，仅渲染末帧）让这一步极快， 同时 -t（透明）确保 PNG 可以无缝嵌入任意背景。

第二次调用 manim -ql 渲染完整动画为 MP4。两次调用共享 --disable_caching 和 --progress_bar none 标志： 前者避免缓存导致的陈旧产物，后者让脚本输出保持简洁。 两次渲染的中间产物都存放在 media/ 临时目录中，由 newest() 函数按修改时间定位最新匹配文件，再拷贝到 out/ 的最终位置。

质量校验是不可跳过的守门环节。PNG 校验使用 Pillow 读取 alpha 通道直方图， 三个阈值确保产物有效：透明像素 > 8%（真的有透明背景，而非全不透明）、 可见像素 > 2.5%（不是空白图）、色彩丰富度 > 1600 像素（不是单色占位图）。 视频校验使用 ffprobe 读取时长，写入 JSON 报告。 任何一项失败都会抛出 RuntimeError，中断整个渲染流程。

设计权衡：为什么不一次渲染同时拿 PNG 和 MP4？因为 Manim 的 -s 末帧模式 走的是 Cairo 光栅化路径（速度快、alpha 精确），而视频渲染走 FFmpeg 编码路径。 分开调用可以各自独立调优参数，且末帧 PNG 的视觉质量与视频末帧不完全等价—— 前者是专门为静态嵌入优化的。

质量保障闭环

图 3 · 三层质量保障体系
从代码静态检查到渲染时校验，再到契约测试，三层防护确保产物完整性。

三层同心圆式的质量保障，由内向外分别对应交付层、渲染层和代码层。 中心是最终交付的 out/ 产物——所有质量工作最终都指向这 24 个文件的正确性和完整性。

最内层（代码层）：ruff 静态检查。确保 Python 代码符合风格规范、 无未使用导入、无潜在逻辑问题。这是最轻量的一层，运行耗时毫秒级， 在开发迭代中可以高频执行。

中间层（渲染层）：渲染时像素级校验。这是最核心的质量门—— 它不检查代码，而是检查产物本身。通过 Pillow 分析 PNG 的 alpha 直方图和色彩分布， 可以捕获「场景构建为空」「透明背景没开」「渲染失败但产出了空白帧」等 仅靠文件存在性检查发现不了的问题。视频时长校验则确保动画不是 0 秒的空文件。

最外层（交付层）：pytest 契约测试。test_contract.py 只有一个测试函数，但它守住了最关键的契约：场景数量不少于 12 个， 每个已注册场景都有对应的 PNG 和 MP4 文件，且视频大小超过 10KB。 这层测试在 CI 或克隆仓库后可以快速验证产物完整性，无需重新渲染。

主走查：渲染单场景

主走查
渲染单场景（以 algorithm-trace 为例）

从命令触发到产物落地，一个场景完整经历的五个关键步骤。

  1. 启动渲染脚本。执行 uv run python scripts/render.py， 脚本首先检查 ffprobe 是否可用（缺失则直接退出）， 创建 out/ 目录，然后从 manim_demos.SCENES 字典中按顺序取出第一个条目：("algorithm-trace", "AlgorithmTrace")。
  2. 第一次 Manim 调用（末帧 PNG）。脚本构造命令 manim -ql -s -t --disable_caching --media_dir media --output_file algorithm-trace scenes.py AlgorithmTrace， 以末帧模式渲染透明背景的 PNG 到 media/ 临时目录。 完成后用 newest() 定位最新 PNG，拷贝为 out/algorithm-trace-transparent.png。
  3. 第二次 Manim 调用（完整动画）。脚本构造命令 manim -ql --disable_caching --media_dir media --output_file algorithm-trace scenes.py AlgorithmTrace， 以低质量模式渲染完整 MP4 动画。同样通过 newest() 定位视频文件， 拷贝为 out/algorithm-trace.mp4。
  4. 双重校验。先用 Pillow 打开 PNG，计算透明像素占比（需 > 8%）、 可见像素占比（需 > 2.5%）和色彩丰富度（需 > 1600 像素）； 再用 ffprobe 读取视频时长。两项都通过后，将元数据写入 JSON 报告并打印。
  5. 循环推进 / 结束。当前场景处理完毕，脚本继续处理下一个场景 （fourier-phasors），直到全部 12 个场景完成。 最终打印汇总 JSON 报告。后续可通过 pytest 运行契约测试， 确认所有产物齐全。

设计要点

为什么用单文件承载所有场景？

12 个场景全部定义在 scenes.py 一个文件中，而非按场景拆分为多个模块。 这是一个有意的选择：场景之间共享大量样式辅助函数（如 title_block）和配色常量， 放在一起便于保持视觉一致性，也便于跨场景复用图案元素。 对于演示/示例类项目，单文件的认知成本远低于多模块导航成本。

为什么产物纳入 Git？

out/ 目录下的 PNG 和 MP4 全部提交到版本库。这看起来违反「构建产物不入库」的常规， 但本项目的定位是「可视化参考集」——消费者（文档、幻灯片、网页）需要的是图，而不是构建图的能力。 将产物入库意味着任何克隆仓库的人都能立即使用这些图示，无需安装 Manim、配置 LaTeX、 等待渲染。渲染脚本仍然保留，用于修改场景后重新生成产物。

catalog.json 的角色

catalog.json 是一个纯元数据文件，不参与代码运行。它的作用是「索引」—— 让外部工具或人工浏览可以快速了解每个场景的教学用途、核心问题和标签， 而无需逐个打开视频或阅读源码。这是文档即数据的实践：用结构化 JSON 替代散落在各处的描述文本。
